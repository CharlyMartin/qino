# Lock file

**Status:** stable (current real shape), v1-proposed (Zod schema parity)
**Version:** v1

## Intent

`qino/qino-lock.json` is the single artifact produced by `qino build`. Two consumers:

1. **Runtime getters** — read it once (cached) to resolve content paths and (V1) relationship targets.
2. **Cloud UI (V2)** — fetches it from GitHub to render the editing dashboard. The cloud UI never imports `qino/config.ts` or `qino/collections/*.ts`; the lock file is its only contract with the project.

Because the cloud UI is a downstream consumer over GitHub, the lock file is **JSON, committed to the repo, and forward-compatible**.

## Canonical shape

```json
{
  "qinoVersion": "0.0.0",
  "config": {
    "contentFolder": "src/content",
    "mediaFolder": "public"
  },
  "collections": {
    "authors": {
      "path": "authors",
      "extension": ".json",
      "relations": []
    },
    "categories": {
      "path": "categories",
      "extension": ".json",
      "relations": []
    },
    "posts": {
      "path": "posts",
      "extension": ".md",
      "relations": [
        { "field": "categories[]", "target": "categories", "cardinality": "many" },
        { "field": "author",       "target": "authors",    "cardinality": "one"  }
      ]
    }
  }
}
```

This is exactly the shape committed at `apps/blog/qino/qino-lock.json`. Treat it as the canonical example.

## Field reference

| Field                              | Type                            | Notes |
|------------------------------------|---------------------------------|-------|
| `qinoVersion`                      | string                          | The version of `qino` that produced this file. Used for migration. |
| `config.contentFolder`             | string                          | Mirrors `qino/config.ts`. Path relative to repo root. |
| `config.mediaFolder`               | string                          | Same. |
| `collections.<id>.path`            | string                          | Relative to `contentFolder`. |
| `collections.<id>.extension`       | `".md" \| ".mdx" \| ".json"`    | File extension for entries. |
| `collections.<id>.relations[]`     | array                           | Declared relationships (see `05-relationships.md`). |
| `relations[].field`                | string                          | Field name in the entry. `[]` suffix for arrays (e.g. `categories[]`). |
| `relations[].target`               | string                          | Target collection id. |
| `relations[].cardinality`          | `"one" \| "many"`               | Whether the field resolves to one or many entries. |

V1 will also include:

- `pages.<id>` — see `03-pages.md`.
- `trees.<id>` — see `04-trees.md`.

## Implementation status

- ✅ `apps/blog/qino/qino-lock.json` already has the full shape.
- ⚠️ `packages/qino/src/lib/lock-file.ts` only models `qinoVersion` + `config`. It does **not** yet validate `collections`, `pages`, or `trees`. This must be reconciled — the Zod schema is the runtime gate that getters trust.
- ⚠️ `packages/qino/src/cli/commands/build.ts` only emits `qinoVersion` + `config`. The richer lock file in `apps/blog/` was hand-authored. The CLI must learn to emit it.

These are tracked as code follow-ups, not spec gaps.

## Behaviour

- Hand-editing `qino-lock.json` is **not supported**. It's a build artifact.
- The file is **committed** to the repo. The cloud UI reads it from GitHub.
- Validation happens twice: at write time in `qino build`, and at read time in `getConfig()` (and other getters). Read-time failures tell the user to run `qino build`.

## Open questions

- Should `qino-lock.json` include the Zod schema serialisation (e.g. via `zod-to-json-schema`) so the cloud UI can render forms? Likely yes — needs spec.
- Migration policy when `qinoVersion` changes — automatic on `qino build`, or explicit `qino migrate`?
- Pretty-print vs minified — currently pretty-printed for git diffs. Keep that.

## Acceptance criteria

Done when:

- `LockFileSchema` in `packages/qino/src/lib/lock-file.ts` validates the full canonical shape above (config + collections + relations).
- `qino build` emits a lock file that round-trips through `LockFileSchema.parse()`.
- The lock file in `apps/blog/qino/qino-lock.json` is regenerated by `qino build` and is byte-identical to the hand-authored one (modulo formatting).
