# i18n

**Status:** v2-deferred
**Version:** v2

## Intent

Multi-locale content: a single Qino project hosts the same collections in multiple languages, and getters / the cloud UI know which is which.

## Sketch (not v1)

Opt in via config:

```ts
// qino/config.ts
import { createConfig } from "qino";

export default createConfig({
  contentFolder: "src/content",
  mediaFolder: "public",
  i18n: {
    default: "en",
    locales: ["en", "fr", "ja"],
  },
});
```

Then content fans out by locale:

```
src/content/
├── en/
│   └── posts/
├── fr/
│   └── posts/
└── ja/
    └── posts/
```

Getters take a locale:

```ts
const posts = await getAllPosts({ locale: "fr" });
```

## Why deferred

- The single-locale path must be polished first (relationships, sort, transform).
- i18n changes the slug story: same logical entry, different physical files. That ripples into the lock file, the cloud UI, and the type generator.
- Real V1 use in `apps/blog/` doesn't need it.

## Open questions (held)

- Layout: `<locale>/<collection>/` vs `<collection>/<locale>/` vs frontmatter-driven (`locale: "fr"`)?
- Fallback: if `posts/hello.md` exists in `en` but not in `fr`, does `getPost("hello", { locale: "fr" })` fall back to `en`, return `null`, or throw?
- Translation linkage: can an entry declare `translations: { en: "...", fr: "..." }` so editors can navigate between versions?
- Per-collection opt-out (some collections are locale-agnostic, e.g. `authors`)?

## Acceptance criteria (when V2 lands)

Done when:

- `getAllPosts({ locale })` returns only entries from the requested locale.
- Missing-locale fallback behaviour is configurable per collection.
- The lock file records which collections are localised.
- Generated types account for locale-specific slug unions.
