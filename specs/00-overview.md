# Overview

**Status:** stable
**Version:** v1

## Pitch

Qino is a flat-file Markdown CMS with two surfaces:

1. An **npm package** (`qino`) for developers — typed config, collection, item, and tree definitions, plus a CLI that builds a manifest of the project (`qino-lock.json`).
2. A **cloud UI** for content editors — reads `qino-lock.json` from GitHub to render an editing dashboard, writes content back into the repo. **V2.**

The content lives as plain files on disk: Markdown, MDX, JSON. Nothing is in a database. The repo is the source of truth.

## Why flat-file

- Markdown is portable, durable, and tool-agnostic. No vendor lock-in.
- Local files support offline work, plain-text version control, and strong data ownership/privacy.
- Content moves with the code through PRs, branches, and tags.

## Two-surface model

```txt
┌──────────────────┐         ┌──────────────────┐
│  Developer       │         │  Content editor  │
│  (IDE)           │         │  (browser)       │
└────────┬─────────┘         └─────────┬────────┘
         │                             │
         │ writes config + schemas     │ edits content via UI
         ▼                             ▼
   qino/config.ts                  GitHub repo
   qino/collections/*.ts           (content files)
         │                             │
         │ qino build                  │ commits / PRs
         ▼                             │
   qino/qino-lock.json ◄───────────────┘
         │
         │ read by both surfaces
         ▼
   Consumer app (e.g. Next.js) — calls getMany / getOne at request or build time
```

## Lifecycle

1. **Author time** — developer writes `qino/config.ts` and `qino/collections/*.ts`.
2. **CLI time** — `qino build` evaluates those files and writes `qino/qino-lock.json` (config + collection schemas + relations).
3. **Consumer build/request time** — the consumer app imports getters from `qino/collections/*.ts`. Each getter reads `qino-lock.json` once (cached) for path resolution, then reads content files from disk.

`qino/config.ts` is **never** imported by the consumer app. Its values flow into the consumer through `qino-lock.json`.

## Glossary

| Term           | Definition                                                                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Collection** | A folder of similarly-shaped entries (e.g. `posts/*.md`, `authors/*.json`). Defined with `defineCollection`. Many entries, one schema.                                                      |
| **Item**       | A single, well-known content file with its own URL or role (e.g. `pages/home.md`, `pages/about.md`). Defined with `defineItem`. One file, one schema. Distinct from a one-entry collection. |
| **Tree**       | A hierarchical, ordered set of entries (e.g. a docs sidebar, nested category structure). Defined with `defineTree`.                                                                         |
| **Entry**      | One file inside a collection or tree.                                                                                                                                                       |
| **Slug**       | The path of an entry inside its collection folder, minus the file extension. `posts/hello.md` → slug `hello`. Used as the lookup key for `getOne`.                                          |
| **Asset**      | A media file (image, video, etc.) referenced from content. Lives under `mediaFolder`.                                                                                                       |
| **Relation**   | A typed reference from one collection's entry to another collection's entry, declared in the schema. Resolved by getters when requested.                                                    |
| **Lock file**  | `qino/qino-lock.json` — generated by `qino build`. Contains config + collection schemas + relations. Read by getters and (V2) by the cloud UI.                                              |
| **Getter**     | `getMany` / `getOne` returned by `defineCollection`. Reads disk, validates against the schema, returns typed objects.                                                                       |
| **Schema**     | A Standard Schema validator for frontmatter and raw `markdown`. Qino adds `_meta` after validation.                                                                                         |

## Non-goals

- Not a database. No querying beyond what getters expose.
- No server-side editing in V1. Cloud UI is V2.
- No arbitrary git providers in V1 — GitHub is the integration target.
- No binary diffs / large media handling beyond plain file paths.
- No multi-tenant authoring in V1. Single repo per Qino project.

## User stories

A Markdown CMS becomes attractive to cloud-CMS users when it stops feeling like “files in Git” and starts feeling like a safe, collaborative publishing product.

Keeping Markdown as the storage layer while abstracting Git, frontmatter, build pipelines, and parser quirks behind a strong editorial interface.

1. Editorial workflows are a common gap: scheduling, approvals, permissions, and staging are usually missing or require extra tooling.
2. Localization and media handling can become painful when you have many files, translations, image variants, and preview requirements.
